# 项目开发规则

> 本文档规定项目开发过程中的重要规则和约束

## 📝 文档管理规则

### 🔴 强制规则：统一开发日志

**规则**: 所有开发记录必须写入 `CHANGELOG.md`，**禁止创建新的独立.md文件**

### 🔴 强制规则：代码修改确认

**规则**: 在修改任何代码之前，必须先询问用户是否理解正确，只有在用户确认理解正确后，才能执行修改操作

**适用范围**:

- ✅ 所有代码文件的修改
- ✅ 配置文件的修改
- ✅ 路由文件的修改
- ✅ 样式文件的修改
- ✅ 任何可能导致功能变化的操作

**操作流程**:

1. 📋 分析问题并提出解决方案
2. ❓ 询问用户："我理解正确的[问题描述]是...，请确认我的理解是否正确"
3. ⏳ 等待用户确认
4. ✅ 只有在用户明确回复"正确"或"确认"后，才执行修改
5. 📝 修改完成后，按要求记录到CHANGELOG.md

**重要补充规则**：

- 在用户确认理解正确后，对于该问题的后续操作不再重复询问理解是否正确
- 用户回复"正确"后，直接进入问题诊断和解决阶段

**适用范围**:

- ✅ 新功能开发记录
- ✅ Bug修复记录
- ✅ UI/UX优化记录
- ✅ 重构记录
- ✅ 性能优化记录
- ✅ 配置修改记录

**例外情况**:

- ❌ README.md（项目说明）
- ❌ 核心模块文档（如：供应商管理模块说明.md）
- ❌ API文档

## 🔧 开发规范

### Git提交规范

```
<type>(<scope>): <subject>

<body>

<footer>
```

**Type类型**:

- `feat`: 新功能
- `fix`: Bug修复
- `docs`: 文档更新
- `style`: 代码格式
- `refactor`: 重构
- `perf`: 性能优化
- `test`: 测试
- `chore`: 构建/工具

**示例**:

```
feat(supplier): 添加欠款金额与Excel明细校验功能

- 添加Excel解析逻辑
- 实现金额对比验证
- 添加错误提示

Closes #123
```

### 代码规范

1. **文件命名**
   - 组件: `PascalCase.vue`
   - 工具: `camelCase.ts`
   - 样式: `kebab-case.scss`

2. **函数命名**
   - 事件处理: `handleXxx`
   - 获取数据: `getXxx` / `fetchXxx`
   - 设置数据: `setXxx` / `updateXxx`
   - 布尔判断: `isXxx` / `hasXxx` / `canXxx`

3. **注释规范**

   ```typescript
   /**
    * 函数说明
    * @param {Type} paramName - 参数说明
    * @returns {Type} 返回值说明
    */
   ```

4. **类型定义**
   - 优先使用 TypeScript 类型
   - 接口使用 `interface`
   - 类型别名使用 `type`

### 目录结构规范

```
src/
├── api/           # API接口定义
├── assets/        # 静态资源
├── components/    # 全局组件
├── config/        # 配置文件
├── directives/    # 自定义指令
├── layout/        # 布局组件
├── router/        # 路由配置
├── store/         # 状态管理
├── style/         # 全局样式
├── utils/         # 工具函数
└── views/         # 页面组件
```

## 🚨 黄金规则：功能完整性保证

### 🔴 最高优先级：修复前功能验证

**规则**: 当修改代码完成任务时，必须先保证之前的功能可以正常使用再进行修改，而不是解决一个问题后又产生另一个问题。

## 🔧 代码修改流程规范

### 1. 修改前检查清单

- [ ] **功能验证**: 确认要修改的功能当前状态正常
- [ ] **依赖分析**: 明确修改可能影响的其他功能模块
- [ ] **测试确认**: 验证相关联的功能是否正常工作
- [ ] **备份策略**: 关键修改前考虑备份或版本控制

### 2. 修改过程规范

- [ ] **渐进式修改**: 小步快跑，每次修改一个明确的功能点
- [ ] **实时测试**: 每完成一个小修改立即测试验证
- [ ] **回滚准备**: 如果发现问题，立即回滚到工作状态
- [ ] **影响评估**: 评估修改对其他功能的潜在影响

### 3. 修改后验证清单

- [ ] **原功能测试**: 确保原有功能未受影响
- [ ] **新功能测试**: 验证新功能按预期工作
- [ ] **关联功能测试**: 测试所有可能受影响的相关功能
- [ ] **边界情况测试**: 验证各种边界条件和异常情况
- [ ] **用户体验测试**: 从用户角度验证整体使用体验

### 🎯 具体实施指南

#### 功能修改前必做检查

```typescript
// 示例：修改合同列表前，先验证当前功能
const validateContractListFunctions = async () => {

  // 验证编辑、删除、查看详情等功能

#### 修改风险控制措施

1. **隔离修改范围**: 一次只修改一个明确的功能点
2. **保持向后兼容**: 确保修改不破坏现有API接口
3. **渐进式部署**: 对于复杂修改，考虑分阶段实施
4. **文档同步**: 及时更新相关文档和注释

### 📋 常见错误案例与预防

#### ❌ 错误案例1：删除功能时影响其他功能

**问题**: 删除操作栏的"详情"按钮，导致合同名称点击功能也被移除
**预防**:

- 使用孤立修改：只删除操作栏中的详情按钮
- 保留其他入口：确保合同名称点击功能正常
- 测试验证：测试所有进入详情的入口都正常工作

#### ❌ 错误案例2：修改样式影响功能

**问题**: 修改表格列宽导致某些字段显示异常
**预防**:

- 样式与功能分离：确保样式修改不影响功能逻辑
- 响应式测试：在不同屏幕尺寸下验证显示效果
- 数据完整性：确保所有数据字段都能正常显示

#### ❌ 错误案例3：API修改影响前端功能

**问题**: 修改mock数据结构导致前端解析错误
**预防**:

- 接口兼容性：确保API修改保持向后兼容
- 数据验证：验证前端能正确解析新的数据格式
- 错误处理：添加适当的错误处理机制

## 🎯 问题解决原则

### 🔴 核心原则：优先解决问题

**规则**: 遇到问题时不要尝试绕过，而是优先思考解决问题。如果经过深入思考后仍然无法解决，请先询问是否能采用替换方案。

### 📋 解决问题流程

1. **深入分析问题根源**
   - 识别问题的具体原因
   - 分析可能的解决方案
   - 评估每种方案的优缺点

2. **尝试标准解决方案**
   - 查阅官方文档和最佳实践
   - 尝试推荐的方法和工具
   - 不要跳过标准流程

3. **寻求帮助而非绕过**
   - 如果标准方法遇到困难，主动询问
   - 说明具体的问题和已尝试的方案
   - 请求指导替换方案的可能性

4. **记录解决方案**
   - 无论采用哪种方案，都要记录详细过程
   - 说明为什么选择最终的解决方案
   - 为未来遇到类似问题提供参考

### ✅ 推荐做法

- ✅ 深入分析问题本质
- ✅ 尝试官方推荐的解决方案
- ✅ 遇到困难时主动寻求帮助
- ✅ 详细记录解决过程

### ❌ 禁止行为

- ❌ 遇到问题立即尝试绕过
- ❌ 不理解原理就采用变通方案
- ❌ 不记录问题解决过程
- ❌ 忽略最佳实践建议

## 🔴 黄金规则：优先使用内部组件

### 📦 组件选择原则

**规则**: 开发中应优先使用项目内部已有的组件，只有在内部组件无法满足需求时才考虑外部方案或新开发。

### 🎯 实施指南

#### 1. 组件查找流程

```bash
# 优先查找内部组件
src/components/          # 全局组件目录
src/views/*/components/  # 页面级组件目录
src/utils/              # 工具函数目录
```

#### 2. 常见内部组件优先级

| 功能需求 | 优先使用内部组件 | 外部方案示例             |
| -------- | ---------------- | ------------------------ |
| 图片预览 | `ImagePreview`   | 新窗口打开、第三方预览库 |
| 文件上传 | 内置上传组件     | 第三方上传库             |
| 表格组件 | `el-table` 扩展  | 第三方表格库             |
| 图表显示 | 内置图表组件     | ECharts、Chart.js        |
| 表单验证 | 内置验证规则     | 第三方验证库             |
| 弹窗组件 | `el-dialog` 扩展 | 第三方弹窗库             |

#### 3. 使用内部组件的优势

- **风格统一**: 与项目整体UI风格保持一致
- **性能优化**: 针对项目需求进行过优化
- **维护便利**: 项目内部维护，升级可控
- **功能完整**: 通常已经集成了项目特有的业务逻辑
- **兼容性好**: 与项目现有代码兼容性最佳

### 🔍 查找内部组件的方法

#### 1. 文件搜索

```bash
# 搜索可能的组件文件
find src/components -name "*.vue" | grep -i preview
find src -name "*image*" -type f
grep -r "ImagePreview" src/
```

#### 2. 代码搜索

```bash
# 搜索相关功能的实现
grep -r "图片预览" src/
grep -r "preview.*image" src/
grep -r "upload.*file" src/
```

#### 3. 查看现有实现

```bash
# 查看类似功能是如何实现的
find src/views -name "*.vue" -exec grep -l "preview\|upload" {} \;
```

### ✅ 最佳实践

#### 1. 开发前检查清单

- [ ] **组件调研**: 确认项目内是否有类似功能的组件
- [ ] **功能对比**: 对比内部组件与需求功能的差异
- [ ] **扩展评估**: 评估是否可以通过扩展内部组件满足需求
- [ ] **性能测试**: 测试内部组件的性能表现

#### 2. 组件使用决策树

```
需要实现新功能？
    ↓
是否有现成的内部组件？
    ↓ YES → 使用内部组件（优先）
    ↓
内部组件能否扩展满足需求？
    ↓ YES → 扩展内部组件
    ↓ NO → 考虑新开发（最后选择）
```

#### 3. 扩展内部组件示例

```typescript
// 示例：扩展现有的ImagePreview组件
import ImagePreview from "@/components/ImagePreview";

// 添加自定义功能
const EnhancedImagePreview = {
  ...ImagePreview,
  methods: {
    ...ImagePreview.methods,
    customFeature() {
      // 新增功能
    }
  }
};
```

### 📋 典型应用场景

#### 场景1: 图片预览功能

**需求**: 实现合同附件图片预览

- ✅ **正确做法**: 使用项目内 `ImagePreview` 组件
- ❌ **错误做法**: 使用 `window.open()` 新窗口打开
- ✅ **优势**: 支持多图切换、键盘导航、响应式布局

#### 场景2: 文件上传功能

**需求**: 实现Excel文件上传

- ✅ **正确做法**: 使用项目内上传组件和Excel解析逻辑
- ❌ **错误做法**: 引入第三方上传库
- ✅ **优势**: 已集成项目业务逻辑和错误处理

#### 场景3: 数据表格功能

**需求**: 实现复杂的数据展示表格

- ✅ **正确做法**: 扩展现有的 `el-table` 组件
- ❌ **错误做法**: 引入第三方表格库
- ✅ **优势**: 保持样式一致，减少依赖

### 🚨 违规后果

不遵守此规则可能导致：

- **UI风格不统一**: 不同组件库的视觉风格差异
- **性能问题**: 引入不必要的依赖和代码体积
- **维护困难**: 外部组件升级可能导致兼容性问题
- **代码重复**: 实现项目已有的功能
- **用户体验下降**: 交互方式不一致
